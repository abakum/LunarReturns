## Исправление приоритета свадьбы

До исправления ВК `recordOf` искал только персон, ТГ — сначала персон, затем свадьбы.
Но `recordShownOf` обоих ботов ищет и свадьбы в общем fallback:
это не означает, что ВК вообще не узнаёт свадьбы в ответах.

Исходное расхождение — неоднозначность старого/нового стиля.
Пусть у двух свадеб одинаковое имя пары `А+Б`, даты хранения
`1900-01-01` и `1900-01-13`, первая свадьба идёт раньше в выборке.
Для ключа `А+Б 1900-01-13` ТГ сразу выбирал вторую свадьбу по хранению,
ВК в fallback выбирал первую по отображённой дате нового стиля.
В reply-командах это означает другую выбранную запись; команда далее
работает с её хранимым ключом. Ключ с сохранённым `_` проходит fallback
без точного совпадения в обоих ботах. Проверить этот сценарий отдельным
ожиданием адаптеров и устранить отличие в ВК по согласованию с пользователем.

После исправления для персон и свадеб одинаково:

- `А+Б 1900-01-13` выбирает запись с хранением `1900-01-13`, даже если
  раньше в выборке есть запись с хранением `1900-01-01`.
- `А+Б 1900_01_13` проходит fallback и выбирает запись с хранением
  `1900-01-01`, отображаемую новым стилем как `1900-01-13`.
- Если точного ключа нет, существующий fallback сохраняется; дефисы сами
  по себе не запрещают поиск по отображённой дате.
- Персона с буквально тем же ключом, что свадьба, сохраняет приоритет.

Это намеренное изменение поведения ВК на неоднозначных ключах, без миграции
данных. Точки сохраняют семантику общего fallback, как `_`; отдельный
приоритет точного поиска для дат с точками не вводится.

Прямые потребители ТГ `recordOf`: фокус-кнопки, поиск одиночной персоны,
текст/удаление связи. Поиск отдельно ограничен персонами (`flatHitKey` и
`rec.xref`), связи ожидают ключи персон. В обработчике фокус-кнопок свадьба
может пройти проверку существования, тогда как ВК использует свои пути
разрешения; не объявлять это пользовательским дефектом без воспроизведения
полного сценария создания соответствующего фокуса. Это за пределами правки.

## Отчёт

### Реализация

- `text.cjs`: matcher принимает AFT `>`; точки и `_` нормализуются
  в общем fallback. Проверены квалификаторы на трёх гранулярностях,
  персоны/свадьбы, старый стиль, некорректные формы и порядок совпадений.
- ВК `recordOf` теперь ищет точную персону, затем точную свадьбу.
  Реальное тело функции проверяется в `a3-text-check`, оба адаптера —
  в `sync-check` на двух свадьбах одной пары с разными датами.
  Обёртка `recordAnyOf` делегирует ему без повторной выборки свадеб.
- Reply-regex обоих ботов и regex реакции ВК захватывают `>`.
  `a3-text-check` исполняет реальные regex из исходников для полной,
  месячной и годовой AFT-даты, точек и `_`.
- Дополнительная найденная причина неоднозначности: адаптеры снимали `_`
  до вызова `recordShownOf`, стирая отличие отображённой даты от хранимой.
  Маркер теперь сохраняется до общего fallback в обоих ботах.
  Правила снятия цифры радиуса не менялись.
  Это также восстанавливает приоритет отображённой даты в reply на персон,
  когда рядом существует другая персона с совпадающей хранимой датой.
- Точки остаются формой отображённого ключа (как `_`), не новым
  вариантом точного ключа. Если точного ключа с дефисами нет,
  прежний поиск по отображённой дате сохраняется.
- `AGENTS.md`: явные обязательные аргументы `filePath` и `command`;
  это инструкции формирования вызовов, не исправление кода харнесса.

### Решение о хвосте FAM-xref

По обсуждению с пользователем 2026-11-09:

- Поддержку явного хвоста `~FAM-xref` для однозначного выбора свадьбы
  выделить в отдельную задачу. Возможная форма: `А+Б ~F2 1900-01-13`;
  окончательный синтаксис определить в той задаче. Хвост должен ссылаться
  на FAM (`fx` записи свадьбы), не изменяя имена супругов.
- Сейчас такой пользовательский синтаксис не реализован. Эта запись
  фиксирует направление дальнейшей работы, а не выполненную поддержку.
- Проверки неоднозначных ключей без хвоста сохранить: они проверяют
  приоритет хранимой даты с дефисами и отображённой даты с `_`/точками.
  Замена всех якорей на `~F2` подменила бы эту проверку поиском по FAM.
- `25:00` в текущем REPL-тесте — только технический способ получить
  сообщение-якорь без upsert свадьбы, не рекомендуемый интерфейсный приём.
  В дальнейшем заменить его подготовкой сообщения-якоря средствами
  стенда без мутации БД; для этого не требуется расширять пользовательский

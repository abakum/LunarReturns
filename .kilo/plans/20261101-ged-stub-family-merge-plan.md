fix(ged): never merge stub-spouse families into one FAM in .ged export (VK + TG)

## Диагноз

В `gedcomText` (lunarreturns.js:2743-2753, копия в tgcloud/lib/bot.js:1363-1373)
семьи дедуплицируются по отсортированному списку pkeys половин:

```js
const s = pkeys.slice().sort();
const m = fams.find(x => x.s.length === s.length && x.s.every((p, i) => p === s[i]));
```

Если у семьи обе половины — заглушки (бездатные супруги без своей записи,
`pkeys` пуст), то `s = []` у ВСЕХ таких семей, и все они сливаются в одну
гигантскую FAM: в неё стекаются все их заглушки-половины (`m.stubs`), дети
(`m.children`, `m.kstubs`), браки и заметки. В экспорте каждая
заглушка-половина этой общей семьи печатает `1 FAMS @F149@` — отсюда
«@X32@ … 1 FAMS @F149@» и сотни (403) записей, указывающих на одну FAM.

Тот же класс баги в `flatRows` (lunarreturns.js:2884-2885, копия bot.js:~1505):
`s` пуст, когда обе половины не нашлись в `indiOf` (в пачке заглушек нет) —
такие семьи тоже сливаются в одну, собирая чужих детей.

## Решение

Семьи без известных (ключевых) половин никогда не мержить: при
`s.length === 0` всегда `fams.push(...)` как отдельную семью. Каждая семья БД
с заглушечными половинами → своя FAM со своими HUSB/WIFE-заглушками и своими
CHIL. Правка в обоих местах обоих файлов:

1. `gedcomText` в `lunarreturns.js` (~2744): `const m = s.length && fams.find(...)`.
2. `gedcomText` в `tgcloud/lib/bot.js` (~1364): то же.
3. `flatRows` в `lunarreturns.js` (~2885): `const m = s.length && fams.find(...)`.
4. `flatRows` в `tgcloud/lib/bot.js`: то же.

Решено с пользователем: каноническая перенумерация I/F/X в экспорте сохраняется
(родные xref из fam.xref/indi.xref не печатаются — отдельное решение, не здесь).

Осознанное следствие: повторный импорт того же .ged создаст по FAM на каждую
семью заглушек (раньше они склеивались) — это корректнее: разные F-записи
исходника с одинаковыми бездатными супругами не обязаны быть одной семьёй.

Фрагментный экспорт (hasKeys) не затронут: там `ps.length === 0 → continue`,
`s` всегда непуст.

## Шаги

1. Внести 4 правки (см. выше) с кратким комментарием по месту (стиль файла —
   русские комментарии, без лишнего).
2. `node dev/sync-check.mjs` — обязан проходить (правка в синхронных копиях).
3. Репл-тест интерфейсного слоя: `node dev/repl.mjs --fresh` — сценарий:
   импортировать/составить древо, где есть ≥2 семьи с бездатными супругами
   (заглушками) и детьми; `/gedcom`-путь (в ВК: `node lunarreturns.js test "..."`,
   где экспорт доступен; зеркально в ТГ-репле) — проверить, что каждая семья
   заглушек дала отдельную FAM, у заглушек по одной FAMS, нет FAM с сотнями
   HUSB/WIFE. При правках древа — прогон пачки типа Romanov_family.txt через
   импорт и вывод; полный .ged экспорт — round-trip: экспорт → импорт → экспорт,
   сравнить состав семей.
4. После прогонов: `git checkout -- dev/tg-db.json`.

## Риски

- Нумерация FAM в .ged сместится (семей станет больше) — это и есть цель;
  пачки .ged.txt не меняются (там другой код, кроме пункта 3, где пачка
  перестанет терять детей склеенных семей — улучшение).
- famsByGenerations получает больше семей с заглушечными половинами — порядок
  поколений должен остаться стабильным (заглушки участвуют как xref-узлы);
  проверить на сценарии из п.3.

## Валидация

- `node dev/sync-check.mjs` — зелёный.
- Репл/ВК-прогон из п.3: число `1 FAMS @...@` на заглушку = числу её семей;
  ни одна FAM не содержит «чужих» CHIL.
- `git status` чист по `dev/tg-db.json`.

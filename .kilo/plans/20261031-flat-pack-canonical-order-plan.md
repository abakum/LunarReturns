# 2026-10-31 — Пачка «-+=»: канонический порядок (экспорт ≈ импорт)

## Задача

Импорт пачки (пример пользователя):

```
-ЗК 1933-02-13 2001-03-27
+
=ЕЯ 1936-02-24
==ИК 1957-05-14
++
И 1957-05-14~
--ГК 1963-05-14
++1987-08-29
ГЧ 1963-07-14
==АК 1990-09-19
++2016-08-27
СА 1992-06-13
```

экспортировался по тапу «-+=» не в исходном виде: линии переставлялись
(безкорневая половина раньше владельца, семьи не по датам), появлялись
лишние «+» (потеря пустых семей), дубли. Причина: порядок вывода
`flatTreeText` зависел от порядка вставки в базу, а односторонние
бездатные семьи воcте пропускались.

## План / что сделано

1. **`flatTreeText(persons, fams, canonical)`** — обе копии
   (`lunarreturns.js`, `tgcloud/lib/bot.js`) дословно:
   - `canonical` включается только для полной пачки чата
     (`chatFlatText` без `keys` — тап «-+=»; радиусные пачки и ветвь
     героя — как прежде, герой первой строкой);
   - ключ семьи: дата свадьбы, без неё — ДР старшего супруга;
   - браки одной персоны — по ключу (solo-бездатные первыми);
   - дети в семье — по возрасту (бездатные в конце);
   - корни-владельцы семей — по минимальному ключу их семей;
     плавающие/остаток — по возрасту.
2. **Голый «+»** выводится и для пустой односторонней семьи (иначе семья
   терялась при обратном импорте); семье с детьми «+» по-прежнему не
   нужен (привязка — к строке родителя, лишний «+» плодил вторую семью).
3. **Досинхронизация ТГ `lib/parse.js`** (драфт оставшийся от 9c2ff56):
   `NOT_FOR_GRAFT` + `noGraft` в `parseTree` — метка пачки ромба
   первой непустой строкой читается и в ВК, и в ТГ.
4. **`dev/sync-check.mjs`** — устаревшие ожидания приведены к формату
   абт-гранулярности (а73f514/4003104, последний раз тест не обновлялся):
   - дубли отчёта: `Тёзка 1960 → Тёзка 1960-01-02~`,
     `Тёзка 1960-01-01~ → Тёзка 1960-01-03~`,
     `Тёзка 1960-01-01 → Тёзка~ 1960-01-01`,
     `Тёзка3 1955-12-31~ → Тёзка3 1956-01-01~`;
   - `STUB_FLAT_EXPECT`: «Мария С 1960-05-10~ (Сарапул) …» (наследство).
   Проверочный вывод при несоответствии печатает сами ♻️-строки.

## Дополнение 2 (тот же коммит) — «семей 4» vs «семей 7»

Диалог дропа считал `weddings` (строки «+»), отчёт — fam-строки базы.
Настоящая причина расхождения — грамматика разбора: **маркерная** строка
того же уровня сразу за «+» («=ЕЯ 1936-02-24») считалась отдельной
персоной, а не второй половиной свадьбы (половиной признавалась только
bare-строка). Пара ЗК+ЕЯ не создавалась, дети вешались на односторонние
«L»-семьи ЕЯ/ЗК (7 fam против 4 свадеб; род-guard «свежий» экспорт
воспроизводил то же самое — идемпотентно, но неверно по сути).

**Фикс** (обе копии `parseTree`: ВК + ТГ `lib/parse.js`): маркерная
строка той же глубины сразу за открытой «+», пол противоположен
владельцу свадьбы — вторая половина (bind, spouseLine, стек не трогаем);
если не привязалась — прежнее поведение (обычная персона). Порядок:
`bindW` → `pw=null` (без повторного flushPw — тот иначе заводил копию
«повторного брака» и стирал жену).

Ваш пример теперь: импорт — «персон 8, семей 4, детей 3», БД — W1
ЗК+ЕЯ (дети ИК/ГК/АК внутри), экспорт «-+=» — дословно исходник
(с той разницей, что половина печатается bare: «ЕЯ 1936-02-24» —
формат бота; «=ЕЯ» тоже принимается). `dev/sync-check.mjs` ✓
(мини-древо/две жены/ошибки не пострадали).

## Дополнение 4 — канонический порядок пачки-ромба 🧬 и вывод её текстом, если влезает

1. **Радиусная пачка 🧬 (ДНК) — тот же канонический рецепт**, что у целого
древа: `chatFlatText(keys)` в обеих копиях теперь вызывает
`flatTreeText(..., true)` (было `false` — героевоцентричный порядок
вставки). Метка `#not for cut and graft` и весь механизм резки-прививки
(`tree.noGraft`, `cutAndGraft`) не менялись. Пачка ветви
(`-+=`/🔗, прививается срезом) по-прежнему герой первой строкой.
Для древа-примера ДНК-выдача стала: ЗК+ЕЯ → ИК+И → ГК+ГЧ → АК+СА —
совпадает с «-+=» и исходным вводом.
2. **Пачка <4000 — текстом в том же ответе, не файлом** (по запросу):
   - **ВК**: правится само сообщение фокуса (`messages.edit`): текст =
     заголовок + пачка, прицепы `.ged`+`.pdf` — всё в **одном** сообщении
     (клавиши фокуса сохранены). Не влезает — как раньше: три прицепа
     `.ged`+`.pdf`+`.ged.txt`, текст не трогается. Фолбэк при недоступности
     правки — тем же одним сообщением текст+прицепы.
   - **ТГ**: правится сообщение с 🔗/🧬-кнопками (`editMessageText`:
     текст = пачка-ромб, клавиатура сообщения сохраняется), прицепы
     `.ged`(+`.pdf`, `(+.ged.txt)` при переполнении) — **одной медиа-группой**
     ответом (ограничение Bot API: подпись прицепа ≤1024, произвольный
     текст + документы в одном сообщении невозможны — это минимальное
     достижимое «в одном ответе»; раньше было 2–3 отдельных sendDocument).
3. Связка пути проверена: `!sendged «ключ» N [>N]`-хук в `dev/vk-repl.mjs`
   (вкл. вариант `>N` — правка сообщения N), mock `messages.edit`
   применяет текст вместе с прицепами. Прогоны: ВК —
   «ged artifacts … (пачка текстом)» и `>2`-правка origin
   (текст-пачка + 2 прицепа в одном); ТГ — правка фокус-сообщения
   пачкой + медиагруппа прицепов; `sync-check` ✓.
   `dev/vk-db.db`/`dev/tg-db.json` возвращены.

# Цель

Для сценария «🧬 (`foc:tree`) в чате A, `/html1` или `/` в чате B» отличить ожидание доставки VK, блокировку Node.js, очередь конкретного чата и задержку отправки ответа. `команда:` сейчас отмечает разбор команды, а не её отправку; `ответ отправлен` печатается до очереди отправки. Очереди входящих уже разделены по `peer_id`; `void run()` у экспорта не переносит вычисления в другой поток.

Сначала автоматический локальный стенд без токена и боевой БД, затем один ручной прогон на реальном VK. Стенд проверяет, что мы видим и различаем причины задержки, и даёт тест для будущей изоляции тяжёлых вычислений. Он не проверяет доступность `lp.vk.com` и не воссоздаёт серверное планирование Telegram.

[Разбор Telegram Serverless на Хабре](https://habr.com/ru/articles/1096488/) полезен как пример разделения доставки, обработчиков и общей библиотеки. Он описывает V8-изоляты, но не раскрывает диспетчер и не подтверждает параллельный запуск между чатами. В VK эти роли уже разделены логически: `longPollStep` принимает обновления, `byPeer` задаёт порядок, обработчики вызывают общий канон `tgcloud/lib/*.cjs`. Разнос обработчиков по файлам не изолирует синхронные вычисления. Если стенд и боевой замер подтвердят эту причину, переносить в воркеры чистую подготовку экспорта, оставляя Long Poll, порядок по чатам, отправку и запись SQLite в основном процессе. В текущий этап воркеры не входят.

# Реализация

1. В `lunarreturns.js` добавить узкий диагностический режим `LOG_VK_TIMINGS=1`, независимый от `LOG_RAW`/`LOG_UPDATES`. Единый префикс `vk timing`, одна строка на событие. Длительности мерить монотонными часами (`performance.now()`), время отправки из `msg.date` сопоставлять с `Date.now()` (секундная точность VK, возможен сдвиг часов). Не писать текст, payload, персональные ключи, имена файлов, URL и токены; только тип/этап, идентификаторы чата и события и тайминги.
2. `longPollStep`: измерять длительность запроса до получения и разбора ответа. Логировать непустую пачку, `body.failed` и ошибки/таймауты, включая полную длительность, но не пустые успешные опросы. Сразу после разбора снять локальное время получения. Для каждого принятого события передавать метку в `byPeer`; логировать вход в обработчик (до `run`), ожидание от получения пачки до запуска, длительность и результат обработчика. Коррелировать по `peer_id`, типу, `conversation_message_id`/`msg.id`, для кнопок также по доступному `event_id`. Для сообщений с валидным `msg.date` писать время VK и возраст на момент получения; для callback без исходного времени возраст не вычислять. Для повторов `catchUp` при необходимости отметить отдельный источник, не выдавать их за Long Poll.
3. В `queueSend` измерять ожидание и время от начала отправки до ответа API или ошибки, включая повторные попытки. Использовать уже имеющиеся идентификаторы ответа (`peer_id`, привязку к исходному сообщению при наличии, `random_id` для самой отправки); не сериализовать параметры запроса. В `sendGedArtifacts` отдельно измерить подготовку файлов, загрузку и завершение всего фонового экспорта: `byPeer` заканчивает измерять обработчик раньше, чем заканчивается `void run()`. В `foc:tree` замерить локальную подготовку ключей и росписи до вызова `sendGedArtifacts`. Отмечать завершение и ошибки в существующих ветках, не менять их обработку.
4. Включать только при диагностике таймер контроля цикла событий (например, интервал 250 мс с `unref()`). Сравнивать фактический интервал по монотонным часам с ожидаемым, писать только выбросы от 250 мс с длительностью. Это позволяет отличить долгий сетевой запрос при отзывчивом Node.js от задержки, совпавшей с синхронным этапом экспорта. Не менять очереди, таймауты, SQL, Telegram или архитектуру. Если замер подтвердит блокировку CPU, следующим шагом рассмотреть ограниченный пул `worker_threads` для чистых расчётов по снимку данных: аналог изоляции исполнения Telegram, а не копирование его структуры каталогов. Сетевую доставку и работу SQLite такой перенос сам по себе не исправит.

# Локальный стенд

5. Добавить `node dev/vk-latency-check.mjs`: родитель поднимает минимальный HTTP-имитатор на `127.0.0.1` со свободным портом, дочерний Node запускает обычный `main()` бота с фиктивным токеном, своим абсолютным `LR_DB` во временном каталоге и группой `99`. Подключить через тестовый preload: перенаправлять только `https://api.vk.com/method/` в имитатор, разрешать остальные запросы только на точный loopback origin стенда и отклонять выход наружу. Не вводить продакшен-настройку API для теста и не переносить моки в `lunarreturns.js`. Существующий `dev/vk-repl.mjs` не подходит для этого прогона: он отключает `main()` и вызывает обработчики напрямую. Не переделывать его; взять за образец формы ответов VK.
6. Имитатор обслуживает `groups.getLongPollServer`, `groups.getMembers`, `/poll` (`a_check`, курсор `ts`, пачки с настоящей формой VK) и методы Bot API, нужные выбранным командам/экспорту. Сохранять отметки постановки апдейта и отправки HTTP-ответа в процессе имитатора, а вывод ребёнка читать построчно. Использовать фиксированные peer/ID, запускать сценарии последовательно с чистой БД, связывать шаги событиями протокола, а не случайными `sleep`. На неизвестный метод отвечать явной ошибкой. Ограничить время каждого сценария; при ошибке вывести последние логи обеих сторон, в любом случае остановить ребёнка, закрыть сервер и удалить только временный каталог стенда.
7. Проверить следующие сценарии:

- **Асинхронное ожидание.** Удержать ответ `messages.send` для `/html1` из A. После получения этого запроса выдать через следующий poll ещё одну команду A и `/html1` из B. Обработчик B должен начаться до освобождения отправки A, следующий обработчик A не должен, а API-ответ B задержится общей очередью. Удержание отпустить после входа B; сверить порядок и ожидание очередей по ID, а не требовать мгновенной отправки B.
- **Задержка доставки.** Поставить команду B в очередь имитатора и намеренно задержать выдачу пакета на пару секунд, независимо проверить, что ребёнок в это время отвечает на IPC-пробу. Ожидать длительный poll/возраст апдейта, а не накопленное ожидание очереди чата. Отдельно один раз оборвать соединение `/poll` и проверить лог ошибки и успешную доставку после штатного повтора. Не ждать реальных 35 секунд ради воспроизведения `TimeoutError`; обрыв проверяет ветку ошибки, а не сам таймер abort.
- **Блокировка процесса.** Удержать первую отправку A, выдать вторую команду A и дождаться, пока имитатор примет следующий poll, затем отпустить первую отправку. При старте второго `messages.send` из A тестовый preload посылает сигнал имитатору и один раз синхронно блокирует дочерний процесс примерно на секунду до пересылки HTTP. Имитатор по сигналу отдаёт B в уже ожидающий poll. Проверить, что HTTP-ответ уходит с работающего имитатора до разбора пачки ребёнком, B не стартует до разморозки, а у бота появляется заметный `loop_lag_ms`. Это контроль измерителя, а не доказательство, что именно экспорт вызывает задержку. Повторить сценарий без флага и убедиться, что строк `vk timing` нет, но команды отрабатывают.
- **Реальный расчёт.** По тому же протоколу прогнать `foc:tree` и команду B на небольшой синтетической родословной: заполнить отдельную БД офлайн штатными адаптерами или создать записи через обновления, сформировать фокусное сообщение и использовать сгенерированный payload кнопки. Сымитировать загрузку/сохранение документов и проверять появление этапов экспорта и ответ B. Не требовать, чтобы фактический расчёт на конкретной машине обязательно дал задержку; числовые оценки вывести в сводке. Большую родословную для замеров использовать вручную, не делать скорость условием прохождения теста.

# Отчёт

- В `lunarreturns.js` под `LOG_VK_TIMINGS=1` добавлены JSON-строки `vk timing`: `poll`/`poll_error`, `handler_start`/`handler_done` (в том числе `source: catch_up` при чтении истории), `send_done`, `focus_prepare`, `export_start`/`export_stage`/`export_done`, `loop_lag`. Поля таймингов не включают тексты, имена, ссылки и токены. `age_ms` учитывает секундную точность даты VK и возможный сдвиг часов. `export_stage` измеряет длительность всего этапа по монотонным часам, а не чистое время CPU.
- `dev/vk-latency-check.mjs` запускает реальный `main()` против локального имитатора, с временной SQLite и запретом внешних запросов. Пять прогонов: очереди двух чатов, задержка и переподключение Long Poll, синхронная блокировка с флагом и без него, настоящий HTML-экспорт с параллельной командой во время удержанной загрузки. В последнем прогоне B ждал 405 мс в общей очереди отправки; при задержке доставки входящий апдейт имел возраст 2977 мс, а очередь обработчика заняла 2 мс; при искусственной блокировке B ждал 1409 мс после выдачи HTTP-ответа, измеритель показал задержку цикла 1259 мс. Эти значения иллюстративны и не доказывают причину боевого инцидента.
- Пройдены `node --check` для обоих изменённых JS-файлов, `git diff --check`, `node dev/sync-check.mjs`, два прогона стенда и отдельный `dev/vk-repl.mjs --fresh` (`/html1`, триггер, 🧬, успешная загрузка HTML, изолированная БД). Широкий `node dev/command-button-check.mjs` завершил TG-часть; общий запуск прерван лимитом 180 с до результата VK-части. Боевой VK, TG и их базы не менялись.

## Расширение: интерактивный Long Poll и большая ветвь

1. Добавить в существующий VK REPL режим `--long-poll`: имитатор слушает loopback, дочерний процесс запускает `main()`, пользовательские события проходят через `/poll`. Сохранить нумерацию команд и кнопок, ответы, импорт файлов и реакции; добавить `!chat` и `!post` для параллельных сценариев. Прямые отладочные вызовы вне протокола не выдавать за Long Poll. По умолчанию использовать отдельную тестовую БД. Обычный REPL и его тесты оставить совместимыми.
2. В автоматическом стенде добавить большую синтетическую ветвь, штатный `foc:tree` и доставку `/html1`, `/` по сигналу начала реального синхронного этапа HTML. Не имитировать вычислительную задержку и не задерживать загрузку в этом сценарии. Сопоставить время выдачи пакета, завершения вычислений и старта обработчиков. Не превращать конкретную скорость машины в критерий успешности.

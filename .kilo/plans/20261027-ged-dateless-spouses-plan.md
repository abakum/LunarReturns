# Без ДР-супруги из .ged + места персон в экспортах — план

Дата: 2026-10-27. Статус: закрыт — реализовано и протестировано (отчёт ниже);
деплой ТГ отложен до публикации (нет tgcloud-логина на этой машине).

## Проблема

При импорте .ged персона без даты рождения выбрасывается целиком
(`lunarreturns.js:2197`, условие `!ind.name || !ind.birt || !ind.birt.date`):
супруг без ДР теряется, семья остаётся «наполовину». Кроме того, места персон
(рождения/смерти) не поддерживаются ни в .ged-импорте (parseGedcom читает
PLAC только у MARR/DIV, `:696–698`), ни в плоском древе (tail персоны без
места, `:2528–2532`), ни в .ged-экспорте (`gedcomText:2322–2327` — только
DATE/TIME). В PDF-диаграмме бездатные не рисуются (`personRows` фильтрует
`birt_d IS NOT NULL`, `:1339`).

## Решения (согласованы с пользователем)

1. **Никаких `_`-плейсхолдеров** (отказались). Безымянные выбрасываются как
   сейчас.
2. **Импорт .ged**: бездатная персона импортируется, если у неё есть имя И она
   упомянута в какой-либо FAM (HUSB/WIFE/CHIL). Хранится как обычная
   dateless-запись `indi` (birt_d NULL — механизм уже есть: stubOf, flatRows
   `nameOnly`, заглушки gedcomText). gedStats (предпросмотр «Да/Нет»)
   считает по тому же критерию.
3. **PDF**: бездатная именованная персона включается в диаграмму — левая
   колонка (год) пустая, бар начинается в году ДР супруга; нет датированного
   супруга — не включается. Подстановка только отображение, в базу ничего не
   пишется.
4. **Плоское древо**: бездатный — строкой «только имя» как сейчас (изменений
   по `_` нет).
5. **Места**: любая дата = `ГГГГММДД [ЧЧ:ММ] (место)` (на входе принимается
   и `ГГГГ-ММ-ДД` — как сейчас, compactDates нормализует; форматы дат не
   менять); известный город
   справочника — сдвиг времени (уже работает в parseTrigger), неизвестный —
   PLAC. Место персоны выводится в плоском древе в скобках за соответствующей
   датой; .ged-импорт читает BIRT/DEAT PLAC и BURI (похороны) как фолбэк.
6. **Место смерти храним**: новая колонка `indi.deat_plac`; то же поле —
   для места/даты похорон при отсутствии смерти (BURI DATE → deat_d,
   BURI PLAC → deat_plac).

## Правки (обе копии: `lunarreturns.js` и `tgcloud/lib/*` дословно)

Порядок задач:

1. **parseGedcom** (`lunarreturns.js:645`, ТГ-копия в `tgcloud/lib/…`):
   - BIRT PLAC → `birt.plac`; DEAT PLAC → `deat.plac`;
   - новый тег `BURI` (1 DATE / 2 PLAC): если у персоны нет DEAT DATE —
     BURI DATE → deat.date, PLAC → deat.plac (иначе BURI игнорируется, если
     DEAT полон: deat.plac заполняется только если пуст).
2. **importGedcom** (`:2192`):
   - персоны с именем+датой — как сейчас;
   - второй проход: бездатные именованные, чей `__xref` встречается в
     `f.husb/f.wife/f.chil` любой семьи — INSERT в `indi` с birt_d NULL
     (deat/plac/note/sex — как есть), добавить в `byId`;
   - fam/links-логика не меняется: `byId.get` теперь находит и бездатных,
     fam получит обоих супругов, links — на обоих родителей;
   - одинаковое «Имя Д»-схлопывание (`:2199`) не трогать — бездатные не
     сливаются по имени (каждый — отдельная запись; повторный импорт того же
     файла создаст дубликаты заглушек — допустимо, как у stubOf-заглушек fam).
3. **gedStats** (`:712`) — критерий как в importGedcom: именованные с датой —
   всегда; бездатные именованные — только если упомянуты в FAM/CHIL; счётчик
   links — дети из `have` (включая бездатных импортируемых).
4. **Схема БД**: `tgcloud/schema.js` — добавить колонку `indi.deat_plac`;
   VK-сторона: убедиться в миграции существующего `db.json`
   (ALTER/ensure-column при старте — по образцу того, как VK создаёт таблицы).
   После деплоя: `npx tgcloud push` → `npx tgcloud migrate`.
5. **upsertPerson** (`:1459`): persisted `rec.plac2` → `deat_plac`
   (UPDATE-ветка `:1474` и INSERT `:1480`).
6. **personRows** (`:1337`): добавить `dp` из `deat_plac` (фильтр birt_d
   NOT NULL не менять — юбилеи/колокольчик не затрагиваются).
7. **flatTreeText.tail** (`:2528`): порядок
   `[ДР, ЧЧ:ММ, (plac), дата смерти, (dp), ^note]`; сам вывод бездатных
   (name-only, `:2539`) не менять. Обратный разбор уже работает: parseTrigger
   читает `(место)` за каждой датой (plac/plac2, `:607/:617`).
8. **gedcomText** (`:2322`): `2 PLAC` под BIRT (r.plac) и под DEAT (r.dp);
   dateless-заглушки X1/X2… уже экспортируются с NAME/FAMS — не менять.
9. **PDF**: `chartFor` (`:3191`) — ряды персон дополнить бездатными именованными
   (отдельный запрос по `birt_d IS NULL AND name != ''`); entry вида
   `{name, birth: null, anchor: <год ДР датированного супруга из fam>|null,
   death, sex}`; `chartModel` (`chartPdf:3018`, проверить при реализации):
   birth=null → пустой ярлык года, позиция бара от anchor; без anchor — ряд
   не включается. `phantoms`/`bornOf` не менять (dateless пропускаются).
   rel-ярлыки родства для бездатных не строятся (нет ключа «Имя Д»).
10. **dev-тесты** (обязательны по AGENTS.md):
    - `node dev/sync-check.mjs` — после правок логики;
    - `node dev/repl.mjs --fresh` — сценарии: импорт .ged с бездатным супругом
      (предпросмотр → Да → /gedcom → round-trip), пачка с местами персон,
      PDF-чарт с бездатным супругом (chartFor в repl доступен);
    - зеркально ВК: `node lunarreturns.js test "..."`, `node dev/vk-repl.mjs
      --fresh`; вернуть `git checkout -- dev/tg-db.json`;
    - деплой: `npx tgcloud status` → `push` → `migrate` (менялась schema.js).

## Риски / заметки

- `keyOfXref`/`xrefOfKey`/`upsertPerson` ищут по `birt_d IS NOT NULL` —
  бездатные остаются «ключевыми null» везде вне fam/stub-механики; не
  «чинить», юбилеи их по-прежнему не видят (personRows).
- ВChartModel надо проверить рендер пустой левой колонки (year label "") —
  text-оператор уже пропускает пустые глифы, но модель может делить ширину
  колонки по тексту.
- Замена ветви пачкой (cutAndGraft) с бездатными: строки «только имя» уже
  проходят applyTree — не ломать.
- Правки синхронно в двух копиях; sync-check — приёмочный тест.

## Вне объёма

- `_`-плейсхолдеры (отменены пользователем).
- Слияние бездатных при повторном импорте .ged (дубликаты допустимы).
- Юбилеи/колокольчик для бездатных (невозможно без ДР).

## Отчёт (2026-10-27)

Реализовано всё из плана, в обеих копиях дословно:

1. **parseGedcom** (`lunarreturns.js`, `tgcloud/lib/parse.js`): BIRT/DEAT/BURI/MARR/DIV PLAC;
   BURI (1 DATE / 2 PLAC) — фолбэк смерти: дата и место заходят в deat, когда
   своей нет (место — только если своё пусто).
2. **importGedcom / gedStats** (`lib/bot.js`, ВК-копия): бездатные именованные
   импортируются, если упомянуты в любой FAM (HUSB/WIFE/CHIL); INSERT с
   `birt_d NULL`, сохраняют deat/plac/death-plac/sex/note; gedStats считает
   по тому же критерию (`famRefs`). Датированные продолжают схлопываться
   по «Имя Д», бездатные — нет; повторный импорт того же файла — дубликаты
   заглушек (согласовано, допустимо).
3. **Схема**: `tgcloud/schema.js` — новая колонка `indi.deatPlac`
   (`deat_plac`). ВК-сторона хранит то же поле в собственном db.json
   (VK-механизм колонок не требует ALTER). После деплоя нужен
   `npx tgcloud push` → `npx tgcloud migrate` — **ещё не выполнено**.
4. **upsertPerson**: `rec.plac2` → `deatPlac` (UPDATE и INSERT);
   **recOfIndi/personRows**: `dp` из `deatPlac` — во все витки данных.
5. **flatTreeText.tail** (обе копии): `[ДР, время, (plac), дата смерти, (dp),
   ^note]`; время при наличии места — исходное (местное), без места —
   московское (h/m), как прежде. Вывод бездатных (name-only) не менялся.
6. **gedcomText** (обе копии): `2 PLAC` под BIRT (r.plac) и DEAT (r.dp);
   заглушки-супруги (`stubs`) и заглушки-дети (`kstubs`) — единым
   `stubInfo` с именем, полом, смертью и местом; бездатному ребёнку —
   `1 CHIL` + `1 FAMC` у заглушки; HUSB/WIFE по полу заглушки.
7. **PDF-чарт** (`tgcloud/lib/chart.js` + ВК-копия): бездатные с якорем
   (год ДР датированного супруга первой семьи, `chartFor`) — строка с пустой
   колонкой года, бар от якорного года, «лет прожито» не выводится, ярлыки
   родства не строятся; без якоря или вне скоупа фрагмента — не рисуется;
   коллизия якоря с ключом датированной тёзки — невидимый суффикс « »,
   дубль датированных по-прежнему ошибка. `persons` в caption теперь по
   `rows` (включая бездатных с якорем), `chartFor` не даёт «персона 2» при
   4 строках.

### Тесты

1. `node dev/sync-check.mjs` — ✓ ВК и ТГ синхронны (23 триггера + гедком/
   плоское древо/связи/chart). Добавлены блоки 3б: бездатные супруги/дети,
   места, похороны (gedStats=4 персоны/1 связь), пачка с местами
   (ожидаемая дословная), BURI→DEAT в экспорте, round-trip пачки и
   round-trip .ged; chartModel/chartPdf: якорь, пустая колонка, отсутствие
   «лет прожито», бары от якоря, коллизия якоря, чарт по импорту бездатных.
2. `node dev/repl.mjs --fresh` (ТГ) — сценарий spouses.ged
   (Иван 1960 (Пермь) + Мария без ДР, смерть (Курск); их дочь Ольга 1985 +
   Пётр без ДР, смерть 2019 (Казань)):
   - дроп → предпросмотр «персон 4…» (бездатные посчитаны) → гед:rep,
     `!dump`: Мария/Пётр в `indi` с birtD NULL, deatD+deatPlac;
   - `/links`: обе بدونдатные половины — bare-строками под своими свадьбами,
     места датированных — в скобках;
   - 🧬 → .ged + .pdf, «4 персон»: экспорт — заглушки X1/X2 с полом,
     DEAT DATE+PLAC (Курск/Казань), `1 FAMC` у детей-заглушек не нужен
     (в этом сценарии их нет), STUB-семейный HUSB/WIFE по полу;
   - round-trip: реимпорт выведенного .ged → та же пачка дословно.
3. `node dev/vk-repl.mjs --fresh` — зеркально: дроп spouses.ged →
   «персон 4, семей 2, детей 1», гед:rep без ошибок.
4. Репл-базы возвращены: `git checkout -- dev/tg-db.json` (vk-db.db —
   gitignore, ребилдится).
5. **Миграция ВК** проверена на честной «старой» базе (sqlite c таблицей
   `indi` без `deat_plac`): при первом обращении (`LR_DB=… node
   dev/vk-repl.mjs`) ensure-цикл в `sq()` делает
   `ALTER TABLE indi ADD COLUMN deat_plac TEXT` — колонка добавлена,
   данные не затронуты. Для ВК ручных действий нет: бот
   само-мигрирует при старте.

Примечание: 🧬-тост «связей пока нет» для trees, где единственный ребёнок
без ДР — прежнее поведение (edges строятся только для датированных ключей
«Имя Д»), не регрессия этого плана.

feat(vk): parallel update dispatch per chat, WAL sqlite (long poll no longer serial)

# Проблема

VK-бот обрабатывает обновления long poll строго последовательно:
`for (const upd of body.updates) { await handleEvent/handleMessage/... }`
(lunarreturns.js:4396-4435). Тяжёлая операция в одном чате (импорт древа
на тысячи персон, PDF, пачки) блокирует бота целиком: другие чаты не
получают ни сообщений, ни кнопок. Отчасти смягчено транзакцией и мгновенным
тостом (правка 3), но последовательность осталась. Плюс синхронный
`node:sqlite` ставит на паузу весь event loop на каждое тяжёлое вычисление.

Решение пользователя: разнести обработку по чатам (параллельность), заодно
включить WAL SQLite (согласовано).

# Ограничения / инварианты

- VK-транспорт только: у ТГ параллелизмом управляет платформа
  (tgcloud), туда не лезем.
- Публичные сигнатуры `handleMessage/handleEvent/handleReaction` и
  sync-экспорты (`VK.importGedcom`, `applyTree`, …) не менять — sync-check
  и реплы вызывают их синхронно.
- Порядок обновлений **внутри одного чата** сохранять (состояние древа,
  `gedPending`, toggle-логика кнопок опираются на порядок); между чатами
  порядок не важен.
- Единое SQLite-соединение: гонки записи не страшны (драйвер sync,
  «критические секции» DB-операций внутри одного обработчика идут без
  await между собой — не перемежаются). Проверить при реализации, что это
  так для путей: `replaceWithGedcom` (BEGIN..COMMIT — сплошной sync-блок
  после `await` резерва), `handleTxtDrop` (резерв до очистки).

# Изменения (lunarreturns.js, VK)

1. **Диспетчер с очередями по чату.** Рядом с long poll-циклом:
   ```js
   const peerChains = new Map(); // peerId -> промис последней задачи
   const byPeer = (peerId, run) => {
       const next = (peerChains.get(peerId) || Promise.resolve()).then(run);
       peerChains.set(peerId, next.catch(() => {}));
       return next.catch(e => console.error("handle:", e.message, ...));
   };
   ```
   В цикле обновлений (4396-4435) вместо `await handleX(...)`:
   `byPeer(peerId, () => handleMessage(...))` и т.д. для message_new /
   message_event / reaction. `lp.ts` двигается как сейчас (до обработки) —
   ВК сам не повторит доставленные обновления. `try/catch` вокруг
   диспетчеризации остаётся для синхронных бросков.
2. **WAL при открытии БД** в `sq()` (после CREATE TABLE, рядом с
   `convertOldDb`): `sdb.exec("PRAGMA journal_mode=WAL");
   sdb.exec("PRAGMA synchronous=NORMAL");` (journal_mode персистентный,
   synchronous — на соединение). Комментарий: скорость записи + чтения не
   блокируются записью; цена — возможный откат последнего коммита при
   обрыве питания.
3. Не забыть: `TEST_MODE` (`:memory:`) — WAL-прагмы на in-memory безвредны
   (journal_mode вернёт memory), выполнять безусловно, результат не проверять.

# Что НЕ делаем

- Переписывать sync-импорт в async/чанковый: транзакция + WAL уже снимают
  2 минуты до секунд; остаточная блокировка event loop на секунды
  приемлема для персонального бота. Если когда-нибудь станет тесно —
  отдельная задача (worker_threads не нужен: один writer SQLite всё равно).
- TG-зеркало: платформа сама разруливает параллельные апдейты.

# Проверка

1. `node dev/sync-check.mjs` — должен остаться зелёным (ничего из чистой
   логики не менялось).
2. `node dev/vk-repl.mjs --fresh` — прогон сценариев: триггер, кнопка 🔔,
   `!ged` + «Да» (транзакция + тост «идёт замена древа…»), правка reply'ем
   (коллизия «~xref»), `!dump` — данные целы, кнопки работают.
3. Два репла параллельно на одну БД не проверяем (WAL multi-process —
   опционально руками); основной признак после деплоя: в journalctl во
   время импорта большого .ged приходят «кнопка: …» других чатов без
   задержки, ошибок «database is locked» нет.
4. Деплой вручную (`systemctl restart lunarreturns`), наблюдение по логам.
5. Отчёт дописать в этот файл (правка 4).

# Риски

- «database is locked» при параллельной записи двух чатов: WAL+NORMAL
  сводит к минимуму; sync-драйвер сериализует запись в пределах процесса.
  Если появится — добавить busy_timeout (`PRAGMA busy_timeout=3000`) —
  предусмотреть в той же правке сразу (безопасно, одну строку).
- Гонки логики между чатами: устраняются sync-непрерывностью DB-блоков;
  при реализации перечитать пути с `await` внутри мутаций древа
  (гед-дроп: `await` только до `gedPending.set` и до BEGIN).

# Отчёт (2026-11-03, правка 4)

Реализовано по плану, оба пункта + busy_timeout:

- **byPeer-диспетчер** перед `longPollStep` (lunarreturns.js): карта
  `peerChains`, `byPeer(peerId, run)` — обновления разных чатов уходят
  параллельно, внутри чата — цепочкой (порядок сохранён). В цикле long poll
  `await handleX(...)` заменены на `byPeer(...)`: message_new (вся ветка —
  action/gedDoc/txtDoc/текст — одной задачей чата), message_event,
  reaction. Ошибки задачи пишутся в лог как раньше. `lp.ts` двигается как
  раньше (до диспетчеризации). `catchUp` не тронут — он завершается до
  старта poll, конкурентности с live-обновлениями нет.
- **WAL**: в `sq()` после CREATE — `PRAGMA journal_mode=WAL` (персистентный),
  `PRAGMA synchronous=NORMAL` и `PRAGMA busy_timeout=3000` (на соединение;
  страховка от «database is locked» из плана добавлена сразу).
- Транспортные проверки из правки 3 не сломаны: `!ged` + «Да» — тост
  «идёт замена древа…» мгновенно, замена в одной транзакции, отчёт
  «✅ древо…» правкой сообщения.

Проверки: `node --check` ✓; `node dev/sync-check.mjs` ✓ (чистая логика не
затронута); vk-repl (LR_DB=/tmp/kilo/nox-vk.db, fresh): триггер → `!ged` →
«Да» → тост сразу, в БД `journal_mode=wal`, все 6 персон на месте
(«Иван ~I3», «Дед ~I5», «Баба ~I6»), 🔔-клавиатура жива. Ранний прогон
без `LR_DB` писал в gitignored `dev/vk-db.db` — игнор, оттуда же выяснено,
что `--db` у vk-repl читается только из env (шапка врёт — вне объёма).

После деплоя: `systemctl restart lunarreturns`; признак работы — во время
импорта большого .ged в логе идут «кнопка: …» других чатов без паузы.

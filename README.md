# LunarReturns

Страница <https://abakum.github.io/LunarReturns/> показывает лунно-солнечные
юбилеи дней рождения и других событий: какие признаки исходной даты
повторяются в её ежегодные календарные годовщины.

При выборе события выводятся имя, дата, время (если задано) и число лет
в текущем году. Для пары со знаком `+` в имени добавляется название
свадебной годовщины. Затем идёт легенда исходного события: солнечный знак
зодиака, животное 12-летнего цикла, день недели, лунный знак зодиака,
фаза Луны и номер с названием титхи (лунного дня), с указанием растущей
или убывающей половины лунного месяца.

Ниже — исходный год и годы годовщин. В каждой строке символами отмечены
совпадения с исходным событием по пяти признакам: животному 12-летнего
цикла, дню недели, лунному знаку, фазе Луны и титхи. Несовпавшие признаки
пропускаются; солнечный знак показан в легенде, но отдельно не учитывается
в числе совпадений. Отметка `²` у лунного знака исходного года означает,
что он совпадает с солнечным.

Кнопка `⋯` / `⋮` переключает сжатый и подробный режимы: для прошлых лет
до возраста 90 лет показываются соответственно двойные и более совпадения
или все годы хотя бы с одним совпадением. Начиная с текущего года в обоих
режимах выводятся годы хотя бы с одним совпадением до первого подходящего
будущего года включительно. Текст расчёта можно скопировать или показать как QR.

Пары «Имя + День рождения» хранятся в localStorage браузера; их можно добавлять,
изменять, удалять, показывать как QR и вставлять из буфера обмена. Размер базы
ограничен ёмкостью QR версии 40 (L, byte) — 2953 байта UTF-8. После входа через
Яндекс базу можно сохранять/загружать в бакет Yandex Object Storage `lunarreturns`
в отдельный объект пользователя. Если облачного объекта ещё нет и Яндекс возвращает
дату рождения пользователя, при загрузке создаётся событие «Я» вместо «Ада».
Секреты облачных функций передаются через переменные окружения; страница и
репозиторий их не содержат. Список событий сохраняется в Yandex Object Storage;
в VK Mini App используются также хранилище и API ВК.
Имена, даты рождения и списки событий push-провайдерам не передаются.
Web-Push отправляется без тела; текст уведомления формируется на устройстве
из локальной базы. ВК получает идентификаторы получателей и общий текст
без сведений о событиях. Для доставки используются технические идентификаторы
подписок; это не означает полного отсутствия обработки персональных данных.

## Состав

- `../abakum.github.io/LunarReturns/index.html` — страница (весь расчёт инлайн, `qr/qrcode.js` локально).
- `../abakum.github.io/LunarReturns/qr/qrcode.js` — [qrcode-generator](https://github.com/kazuhikoarase/qrcode-generator) v1.4.4 (MIT), vendored.
- `function/handler.py` — облачная функция Yandex Cloud Functions (Python, только stdlib):
  проверяет OAuth-токен через `https://login.yandex.ru/info` и выдаёт presigned URL
  (SigV4) на `GET`/`PUT` объекта с базой пользователя. Подпись сверена
  побайтово с boto3 `generate_presigned_url`.
- `function/push.py` — web-push и уведомления VK Mini App, ежедневный запуск таймером YC.
- `lunarreturns.js` — VK-бот с локальной SQLite-базой и systemd-установщиком.
- `tgcloud/` — Telegram-бот и канонические общие модули обоих ботов (`lib/*.cjs`).
- `dev/` — офлайн-реплы и проверки синхронности VK/TG.
- [`-+=.md`](./-%2B%3D.md) — формат «Родословная роспись -+=» и рецепт
  повторяемой генерации.
- [`pdf.md`](./pdf.md) — правила радиуса 1–5: кровный обход и супруги,
  семейный контекст PDF и отличия от `.ged`, росписи и списка.

## GEDCOM И TXT Из Командной Строки

Офлайн-конвертеры используют тот же канон `parse.cjs`/`flat.cjs` и адаптеры
импорта/экспорта, что и боты. Требуется Node.js ≥ 22.5 (`node:sqlite`);
токены, облако и внешние зависимости не нужны. SQLite работает только в памяти,
закрывается после преобразования и не читает/меняет `lunarreturns.db`,
`dev/tg-db.json` или БД из `LR_DB`.

Установка ссылок на команды из корня репозитория без `sudo`:

```sh
npm_config_prefix="$HOME/.local" npm link
export PATH="$HOME/.local/bin:$PATH"
```

Чтобы команды были доступны в новых терминалах, добавьте строку
`export PATH="$HOME/.local/bin:$PATH"` в `~/.bashrc`, если её ещё нет.
Обычный `npm link` тоже подходит, если глобальный префикс npm доступен
пользователю. При системном префиксе `/usr` он выдаёт `EACCES`;
вариант выше не меняет глобальные настройки npm и не требует прав root.

После установки:

```sh
ged2txt "my tree.ged"       # создаёт my tree.ged.txt
txt2ged "my tree.ged.txt"   # создаёт my tree.txt.ged
```

Без установки, из корня репозитория:

```sh
node bin/ged2txt.cjs "my tree.ged"
node bin/txt2ged.cjs "my tree.ged.txt"
node dev/ged-txt-cli-check.mjs
```

Каждая команда принимает ровно один путь. Расширения `.ged` и `.ged.txt`
распознаются без учёта регистра; `ged2txt` дописывает `.txt`, а `txt2ged`
заменяет только конечное `.ged.txt` на `.txt.ged`, сохраняя остальное имя
(например, `My.Tree.GED.TXT` → `My.Tree.txt.ged`).
Пути с пробелами заключайте в кавычки. Вход строго UTF-8 с необязательным BOM,
выход UTF-8 с BOM. Успех печатает выходной путь, ошибка идёт в stderr с кодом 1.
**Существующий выход никогда не перезаписывается**, в том числе ссылка:
исходный `foo.ged` сохраняется, рядом остаются `foo.ged.txt` и `foo.txt.ged`.
Если `foo.txt.ged` уже существует, для нового преобразования используйте
другой stem, например `edited.ged.txt` → `edited.txt.ged`.

Это нормализованное представление, не архив GEDCOM: xref могут измениться,
неподдержанные теги теряются. Импорт GEDCOM может назначать бездатным родственникам
фиктивные даты EST (`~`) и различать тёзок суффиксами имён; не удаляйте эти метки.
В TXT датированные персоны сопоставляются по имени и дате, бездатные по имени;
тёзки без дат неоднозначны. Повторные полные браки одной пары объединяются,
но повторные односторонние семьи, включая пустую семью при известном родителе,
сохраняются отдельно. Семья совсем без персон не представима. Подробности
и остальные ограничения: [`-+=.md`](./-%2B%3D.md). Говорящие примеры GEDCOM
находятся в `dev/fixtures/`; проверка сравнивает нормализованный TXT после
цикла GED → TXT → GED → TXT, а не исходные байты GEDCOM.

## Telegram-бот (tgcloud, серверлесс)

Бот на платформе [Telegram Serverless](https://core.telegram.org/bots/serverless):
`tgcloud/handlers/message.js` (триггеры «Имя ГГГГ-ММ-ДД [ЧЧ:ММ]» — как в VK-боте,
`/today`, `/bell`, импорт дерева), `tgcloud/handlers/callback_query.js`
(кнопки: удаление, подробно, родня, дерево, настройки религиозных дайджестов).
Общая логика VK и TG — единый канон `tgcloud/lib/*.cjs`: астрономия,
религиозные дни, разбор триггеров, родство, дерево, диаграммы и экспорт
родословной росписи `-+=`.
VK загружает эти же файлы через `reqLib()`, TG — через импорты.
Форматирование юбилейного ответа платформенное: TG — HTML со спойлерами,
VK — обычный текст. Схема БД — `tgcloud/schema.js`: таблицы `indi`, `fam`,
`chil`, `edges`, `settings`, `ged_drops`, `focus_view`.
Реакции 👎/👀 из VK заменены кнопками под ответом бота.

Деплой (нужен VPN и бот с включённым Serverless в @BotFather):

```
npx tgcloud login    # токен: @BotFather → бот → Serverless → CLI Access
npx tgcloud push     # залить модули
npx tgcloud migrate  # создать таблицы
```

Запуск локального кода на платформе без публикации:
`npx tgcloud run handlers/message '{ chat: { id: 1 }, text: "Ада Байрон 1815-12-10" }'`.
Офлайн-проверка: `node dev/repl.mjs --private` (подробнее ниже).

Встроенного ежедневного задания у TG-бота нет: `/today` вызывается по запросу
или внешним планировщиком. Это не относится к VK-боту и push-функции YC.
Локальная копия документации платформы: `docs/tgcloud-serverless.md`.

### Создание бота lunarreturns в Telegram (один раз)

Для локальных инструментов проекта используйте Node.js ≥ 22.5.
Если Telegram API или платформа недоступны из вашей сети, потребуется VPN.

1. **Зарегистрировать бота** у [@BotFather](https://t.me/BotFather):
   `/newbot` → имя (например, «LunarReturns») → username
   (например, `lunarreturns_bot`; должен заканчиваться на `bot`).
   Bot API-токен, который он выдаст, **не нужен** — код бота живёт на
   инфраструктуре Telegram и токенов в репо не содержит.
2. **Включить Serverless**: в @BotFather открыть созданного бота →
   **Serverless** → переключатель **on**. Это открывает хендлеры, библиотеку,
   БД и CLI-токен бота.
   Если кнопки **Serverless** нет, откройте **Mini App** бота
   @BotFather и запросите добавление в список ожидания Serverless-беты.
   После предоставления доступа кнопка появится в меню бота.
3. **Получить CLI-токен**: там же → **Serverless** → **CLI Access** →
   **Access token** (вид `app<id>:<secret>`). Токен отдельный, не бот-токен.

### Установка кода бота из tgcloud/ (клон репо на новую машину)

```
git clone https://github.com/abakum/LunarReturns && cd LunarReturns
npm install -g @tgcloud/cli   # CLI 0.2+; либо npx tgcloud везде ниже
npx tgcloud login             # вставить CLI-токен из шага 3 выше
npx tgcloud status            # сравнить локальные модули с облаком
npx tgcloud push              # залить schema/lib/handlers в облако бота
npx tgcloud migrate           # применить схему БД (интерактив, подтвердить)
npx tgcloud webhook           # должно быть In sync с handlers/message, callback_query
```

Токен сохраняется в `.tgcloud/` (gitignored). Обновления кода дальше —
правки в `tgcloud/` → `npx tgcloud status` (что изменилось) →
`npx tgcloud push`; изменения `tgcloud/schema.js` — отдельный
`npx tgcloud migrate` после push.

### Проверка живого бота

1. Открыть бота в Telegram → `/start` → справка + клавиатура
   (в личке: 🗑, 🔔, 🧬, `-+=`, ❌ и религии 🔔/🔕).
2. Отправить «Ада Байрон 1815-12-10» → юбилейный ответ с кнопками 👎/👀;
   повтор с другим временем — обновление, не дубль.
3. `/today` — события и религиозные праздники сегодня (МСК).
4. 👎 под ответом — удаление; 👀 — подробный расчёт.
5. 🔔 или `/bell` — список событий чата; `/bell1`…`/bell5` ответом на
   триггер — список родни в заданном радиусе.

### Радиус Родни И Экспортов

Радиус 1–5 у фокуса персоны ограничивает родню в списке 🔔 и файлах 🧬
(`/bell1`…`/bell5`, `/gedcom1`…`/gedcom5` ответом на триггер).
Сначала выбирается кровная родня: подъём к предкам, затем спуск к их
потомкам **без повторного подъёма после спуска**. Материнские и отцовские
линии равноправны. Супруги добавляются конечным слоем, без обхода их родни:
жена героя остаётся, «жена сына» входит с R2, а «отец жены» или «сестра жены»
не включаются только по брачному пути. Собственный кровный путь сохраняет персону.

PDF дополнительно требует непустой ярлык родства длиной не больше радиуса
(кроме героя). У GED/росписи и колокольчика отбор отличается: например,
неполнородный брат может войти в GED/роспись на R1, но в PDF и уровневый
список — только на R2 при разных известных вторых родителях.
R5 не означает «всё древо». Полный `/gedcom` без героя и роспись ветви `-+=`
не подчиняются этим радиусным правилам. Подробности и примеры — в
[`pdf.md`](./pdf.md).

## Развёртывание

### 1. Приложение Яндекс ID (единственный полностью ручной шаг)

1. <https://oauth.yandex.ru/client/new> → создать приложение.
2. Платформа «Веб-сервисы», Redirect URI: `https://abakum.github.io/LunarReturns/`.
3. Доступы: «Яндекс ID» → «Идентификатор пользователя» (`login:id`);
   для начального события «Я» также нужен доступ к дате рождения (`login:birthday`).
4. Полученный Client ID вписать в константу `YANDEX_CLIENT_ID` в `index.html`.

### 2. Всё остальное — `./deploy.sh` (см. ниже)

Скрипт создаёт и поддерживает: бакет `lunarreturns` (приватный, CORS
`GET`/`PUT` с origin `https://abakum.github.io` и prod/stage-доменов
VK Mini App 54746591, лимит 1 ГиБ), сервисный аккаунт `lunarreturns-fn`
(`storage.editor`) со static key,
функцию `lunarreturns-presign` (python312, `handler.handler`, 128MB / 10s,
публичный вызов) из `function/handler.py`, функцию `lunarreturns-push`
(`push.handler`, 128MB / 120s) из `function/push.py` и таймер
`lunarreturns-push-timer` (ежедневно 06:00 UTC = 09:00 МСК). Вручную эти
команды повторять не нужно; URL функций скрипт сам вписывает в константы
`FUNCTION_URL`/`PUSH_URL`/`PUSH_PUBLIC_KEY` в
`../abakum.github.io/LunarReturns/index.html` (в CI коммитит и пушит
автоматически; локально — вручную).

Переменные окружения функции (документация `function/handler.py`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | статический ключ сервисного аккаунта | — (обязательны) |
| `BUCKET` | имя бакета | `lunarreturns` |
| `ALLOWED_UIDS` | белый список UID через запятую (пусто — пускать всех) | `` |
| `EXPIRES` | срок жизни presigned URL, сек | `600` |

Переменные окружения push-функции (документация `function/push.py`):
`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`/`BUCKET` — как выше,
`VAPID_PRIVATE`/`VAPID_PUBLIC` — VAPID-пара (обязательны; создаются
`vapid-keygen.sh`), `VAPID_SUBJECT` — необязательный `mailto:`.
`VK_APP_SECRET` (защищённый ключ мини-аппа 54746591 — проверка `sign`
launch-параметров) и `VK_SERVICE_TOKEN` (сервисный ключ — отправка
уведомлений `notifications.sendMessage`) — опциональны; без них ВК-действия
(`vk_subscribe`/`vk_unsubscribe`, ежедневная отправка) отключены.
Задаются как GitHub Secrets (`gh secret set VK_APP_SECRET -R abakum/LunarReturns`
и `VK_SERVICE_TOKEN`) или локально экспортом перед `./deploy.sh deploy`.
ВК-подписки хранятся отдельным ключом `push/vk_subs.json` того же бакета
(`[{vk_user_id, dates}]`, даты — MM-DD, без имён и годов рождения;
идентификатор пользователя ВК при этом сохраняется).

### 3. Проверка

1. Закоммитить страницу с заполненными константами (при деплое из CI —
   не требуется, workflow пушит сам), дождаться GitHub Pages.
2. Войти через Яндекс, добавить события, проверить QR и копирование.
3. «Сохранить базу в облако», очистить localStorage (или другой браузер),
   «Загрузить базу из облака».
4. ВК-пуши (после шага «Секреты ВК»): деплой функции → деплой мини-аппа
   из репо страницы → в мини-аппе 🔔 → разрешение → добавить событие с
   сегодняшней датой → проверить `push/vk_subs.json` в бакете → дождаться
   таймера 09:00 МСК (или `yc serverless function invoke lunarreturns-push`)
   → по пушу открыть приложение — автотап покажет сегодняшнее событие.

После каждого деплоя скрипт сам делает smoke-тест URL функции.

## Развёртывание скриптом

Всё, кроме приложения Яндекс ID (шаг 1), делает локальный `deploy.sh`
(нужны `gh`, `zip`, `curl`, `jq`; отсутствующий `yc` скрипт ставит сам в
`~/yandex-cloud` без sudo, а не настроенные `yc init` / `gh auth login`
запускает интерактивно):

- `./deploy.sh` — сам выбирает действие: `bootstrap`, если функции ещё нет
  (бакет с CORS (лимит 1 ГиБ), СА `lunarreturns-fn`
  (`storage.editor`), функция и первая версия из `function/handler.py`),
  иначе `deploy` — новая версия обеих функций (push-функция создаётся
  автоматически при первом `deploy`). Явный аргумент (`./deploy.sh deploy`
  или `bootstrap`) принудителен; обе команды идемпотентны. Для деплоя
  push-функции нужны VAPID-ключи — локально из `.vapid.env`
  (см. `vapid-keygen.sh` ниже); без них и без `.vapid.env`
  команда `deploy` завершается с подсказкой, а `bootstrap` пропускает
  создание push-функции и её таймера.

При каждом запуске скрипт ротирует static key СА: создаёт новый, кладёт его в
GitHub Secrets `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` (через локальный
`gh`, PAT не нужен), передаёт в env функции и удаляет старые ключи (env
функций в логах CI скрывается). Скрипт также вписывает URL функций в
константы `FUNCTION_URL`/`PUSH_URL`/`PUSH_PUBLIC_KEY` в
`../abakum.github.io/LunarReturns/index.html` (страница живёт в репо
abakum/abakum.github.io): из CI — коммитит и пушит сам, локально — commit
и push вручную. Дополнительно можно задать `ALLOWED_UIDS` и `EXPIRES`
(по умолчанию `` и `600`).

### Подготовка секретов ВК-пушей (один раз, локально)

Для ВК-нативных уведомлений мини-аппа 54746591 нужны два ключа из панели
разработчика ВК (<https://dev.vk.com> → ваше приложение → «Разработка» →
«Ключи доступа»):

- **Защищённый ключ** → `VK_APP_SECRET` — серверная проверка `sign`
  launch-параметров (единственный барьер против подделки `vk_subscribe`,
  URL функции публичен).
- **Сервисный ключ** → `VK_SERVICE_TOKEN` — отправка уведомлений
  (`notifications.sendMessage`).

Сохранить их в GitHub Secrets репозитория функции:

```bash
gh secret set VK_APP_SECRET   -R abakum/LunarReturns   # вставить защищённый ключ
gh secret set VK_SERVICE_TOKEN -R abakum/LunarReturns  # вставить сервисный ключ
```

Либо интерактивно (скрытый ввод, существующие секреты не трогает, пустой
ввод — отложить): `./ci-prepare.sh` спросит оба ключа тем же блоком, что
`GH_PAT`. Секреты не ротируются (в отличие от S3-ключей) и читаются только
при создании версии функции. Локальный деплой: экспортировать те же
переменные перед `./deploy.sh deploy`. Без них деплой проходит с
предупреждением, но ВК-действия функции отвечают 500 «not configured».

После деплоя проверить: `curl -d '{"action":"vk_subscribe"}' <PUSH_URL>`
→ 500/403 (не «action must be …»), т.е. vk_-ветка активна.

### Подготовка деплоя через GitHub Actions (один раз, локально)

- PAT для ротации секретов из CI: `GITHUB_TOKEN` не умеет управлять
  секретами репозитория, поэтому `ci-prepare.sh` попросит один раз
  вставить PAT с правом `repo` (создать: <https://github.com/settings/tokens>)
  и сохранит его в секрет `GH_PAT`.
- `./ci-prepare.sh` — выдаёт СА `github-actions` роли
  `serverless.functions.admin` + `iam.serviceAccounts.accessKeyAdmin`,
  создаёт authorized key и кладёт в GitHub Secrets `YC_SA_KEY` /
  `YC_FOLDER_ID`. Идемпотентен. Печатает sa.json на экран — сохраните его
  в менеджер паролей: секрет из GitHub не читается обратно. Потеря ключа
  лечится повторным запуском скрипта (подписки не страдают).
- `./vapid-keygen.sh` — генерирует VAPID-пару для push-уведомлений:
  `VAPID_PRIVATE`/`VAPID_PUBLIC` в GitHub Secrets, `.vapid.env`
  (chmod 600, не в git) — ЕДИНСТВЕННАЯ резервная копия приватного ключа
  (её потеря = потеря всех push-подписок), публичный ключ коммитится
  в `vapid_public.txt`. `--force` — принудительная регенерация
  (все подписки пропадут), `--show-private` — напечатать приватный ключ.

### Деплой из CI

Workflow `.github/workflows/deploy.yml` (Actions → Deploy → Run workflow):
по `workflow_dispatch` деплоит обе функции через `deploy.sh deploy`,
ротирует S3-ключи, обновляет константы в index.html и пушит репо страницы
(для этого workflow чекаутит `abakum/abakum.github.io` с `GH_PAT`).
Локальный `./deploy.sh deploy` работает как раньше:
VAPID — из `.vapid.env` или экспортированных переменных, `yc init` /
`gh auth login` интерактивно.

## VK-бот юбилеев (`lunarreturns.js`)

Бот сообщества ВКонтакте отвечает списком лунно-солнечных юбилеев на сообщение
вида:

```
Костя 19630927
Дедушка Костя 1963-09-27 14:30
Дедушка Костя 1963-09-27 12:30 (МСК+2)
Дедушка Костя 1963-09-27 12:30 (Пермь)
Дедушка Костя 1963-09-27 12:30 UTC+5
```

`+` в имени — пара (`Костя+Галя 19780512`), в годовщины добавляются названия
свадеб (серебряная, золотая…). Город — из списка приложения (учтены
исторические сдвиги часов), сдвиг — `МСК±N` / `UTC±N` / `ГМТ±N`. Без времени
берётся полдень, без пояса — МСК. Расчёт — тот же `la()` из `index.html`.

В одном сообщении можно указать несколько триггеров — по одному на строку;
на каждый бот отвечает отдельным реплаем.

Данные хранятся в SQLite `lunarreturns.db` рядом со скриптом (путь можно
переопределить через `LR_DB`). Источник истины — дерево чата с xref-идентичностью
персон и семей (`indi`, `fam`, `chil`, `links`); события «Имя + дата» —
производные представления. В личном чате можно вести своих знакомых,
а в групповом — общих. Ответ бота идёт реплаем на
триггер (`reply_to` в личке, `forward` в чатах). Каждый год в день события
в 09:00 МСК бот сам отправляет обновлённый список юбилеев в тот же диалог.
После простоя бот догоняет накопившиеся триггеры по истории сообщений
(`messages.getHistory`, как `catchUp` в pinguin), порог — `lastSeen` в базе.

Запуск: Node.js ≥ 22.5 с `node:sqlite` (проверено на 24.15), внешних зависимостей нет:

1. В настройках сообщества: Управление → Работа с API → Создать ключ с правами
   **«Управление сообществом» + «Сообщения сообщества»** (без первого
   `groups.getLongPollServer` отвечает «Access denied»); включить
   «Возможности ботов» и Long Poll API.
2. `VK_TOKEN=vk1.a.... node lunarreturns.js` (или `.env` рядом со скриптом,
   тоже в `.gitignore`). Группа берётся из токена через `groups.getById`
   (как в pinguin). Необязательная `VK_GROUP_ID` (число из `club…`) задаёт
   группу явно и фильтрует события — полезно, если токен многоцелевой.

Проверки без привязки к ВК:

- `node lunarreturns.js test "Дедушка Костя 1963-09-27 12:30 (Пермь)"` — разбор
  (перевод в МСК) и список юбилеев; строки можно перечислять построчно;
- `node lunarreturns.js probe` — с токеном: проверка ключа, диалогов,
  отправки и 2 минуты сырых ответов Long Poll в двух вариантах опроса.

Диагностические флаги: `LOG_VK=1` — сырые ответы VK API и Long Poll,
`LOG_UPDATES=1` — каждое событие и сообщение.

### Кнопки, реакции 👎/👀, религиозные дни

Сообщение `/` (в любом чате) — справка по триггерам, связям и кнопкам:

- **личный чат**: ряд `[🗑 🔔 🧬 -+= ❌]` + ряд `[☦️ ☪️ ☸️ ✝️ ✡️]` (пары
  `[религия 🔔|🔕]`);
- **групповой чат**: владелец сообщества (определяется автоматически по
  `role=creator`) — ряд `[🗑 🔔 🧬 -+= ❌]` без религиозных кнопок;
  остальные — `[🔔 🧬 -+= ❌]`.

Кнопки:

- `🗑` — список записей чата (по возрастанию полных дат) и подтверждение
  `🗑`/`❌`;
- `🔔` — список событий по ММ-ДД, начиная с сегодняшнего дня;
  исходное сообщение редактируется в том же чате, не помещающиеся строки отрезаются;
- `🧬` — генеалогическое дерево; кнопка `-+=` —
  [«Родословная роспись -+=»](./-%2B%3D.md) (формат и рецепт генерации);
- `[религия 🔔|🔕]` — первый тап показывает календарь религии на год вперёд;
  повторный тап по той же религии в показанном календаре переключает оповещения.

Каждый день в 09:00 МСК чаты с включёнными религиями получают список
сегодняшних религиозных дней (если дней нет — ничего не присылается).

**Реакции** на ответы бота и утренние уведомления:

- 👎 — удалить запись с каскадной очисткой связей и отредактировать исходный
  ответ в пометку об удалении (если редактирование не удалось — ответить reply);
- 👀 — развернуть расчёт в исходном сообщении; кнопка 🌙 сворачивает его обратно.

Для прошлых лет до возраста 90 лет сжатый расчёт показывает годы с двумя
и более совпадениями, подробный — с одним и более. Начиная с текущего года
оба режима показывают годы хотя бы с одним совпадением до первого подходящего
будущего года включительно (защитный предел поиска — 500 лет).

Для кнопок и реакций в настройках сообщества (Long Poll API → Типы событий)
должны быть включены «Действие с сообщением» и «Действие с реакциями на
сообщение». Настройки хранятся в SQLite для каждого чата (`settings`).
Идентификаторы реакций заданы в коде: 4 = 👍, 9 = 👎, 32 = 👀.

Проверки религиозных дней без ВК:

- `node lunarreturns.js test rel` — сегодняшний дайджест всех религий;
- `node lunarreturns.js test rel:orth` — православные дни на год вперёд
  (аналогично `rel:cath`, `rel:islam`, `rel:jud`, `rel:bud`).

### Офлайн-проверки VK и TG

- `node dev/sync-check.mjs` — проверка синхронности общей логики VK/TG:
  разбор триггеров, GEDCOM, связи, семьи, каскадное удаление и форматы вывода.
- `node dev/repl.mjs --private` — TG-репл без облака и токена.
- `node dev/vk-repl.mjs` — VK-репл без API ВК и токена.

Команды обоих реплов (`N` — номер сообщения, `M` — номер кнопки;
квадратные скобки обозначают необязательный аргумент):

| Команда | Действие |
|---|---|
| `текст` | Отправить сообщение боту; литерал `\n` внутри строки задаёт перевод строки |
| `>N текст` | Ответить на сообщение N |
| `/N M [uID]` | Нажать кнопку M сообщения N, при необходимости от другого пользователя |
| `!ged путь` | Отправить файл GEDCOM |
| `!txt путь [>N]` | Отправить файл с родословной росписью, при необходимости ответом на сообщение N |
| `!dump` | Показать таблицы тестовой БД |

Дополнительные команды VK-репла:

| Команда | Действие |
|---|---|
| `!ged путь >N` | Отправить GEDCOM ответом на сообщение N |
| `!date ГГГГ-ММ-ДД [час]` | Подменить сегодняшнюю дату по МСК и, при необходимости, час для суточной проверки и списков |
| `!date off` | Вернуть настоящую дату и время |
| `!daily` | Выполнить суточную проверку годовщин и религиозный дайджест |
| `!wait мс` | Подождать завершения фоновых операций, например выгрузки файлов, перед окончанием сценария |
| `!sendged ключ радиус [>N]` | Сформировать файлы дерева, как кнопка 🧬 на фокусе; ключ — `Имя ГГГГ-ММ-ДД` без кавычек, `>N` — редактировать сообщение N |
| `!eyes N [uID]` | Поставить реакцию 👀 на сообщение N, при необходимости от другого пользователя |
| `!eyes N off` | Снять реакцию 👀 |

Выход из реплов — `Ctrl-C`.
Запускать из корня репозитория; `--fresh` сбрасывает тестовую БД.
Тестовые базы реплов по умолчанию хранятся в `dev/`; для изоляции задайте
абсолютный путь через `LR_DEV_DB` (TG) или `LR_DB` (VK).
После правок логики обязательны sync-check и затронутые сценарии в обоих реплах
до публикации в облако.

### Автозапуск (systemd, изолированный системный сервис)

Сервис полностью отвязан от пользователя-установщика: работает под
одноразовым системным пользователем (`DynamicUser`), а скрипт и база живут
в `/var/lib/lunarreturns` — домашние каталоги пользователей сервису
недоступны (`ProtectHome=yes`), поэтому запуск идёт не из клона репо.

Установка — один скрипт (идемпотентен: повторный запуск обновляет скрипт и модули
в `/var/lib/lunarreturns`, юнит и перезапускает сервис):

```bash
sudo ~/src/LunarReturns/lunarreturns-install.sh
```

Он проверит/попросит токен, найдёт node (в т.ч. nvm), скопирует
`lunarreturns.js` и `tgcloud/lib/*.cjs` в `/var/lib/lunarreturns` с сохранением
структуры каталогов, соберёт юнит из шаблона
`lunarreturns.service.in` и поставит его в `/etc/systemd/system/`, включит
автозагрузку и запустит сервис. Логи: `journalctl -u lunarreturns -f`.
Уже существующую SQLite-базу из клона установщик не копирует.

Обновление бота (после `git pull`) — повторный запуск того же скрипта.

Расположение после установки:

| что | где |
|---|---|
| скрипт | `/var/lib/lunarreturns/lunarreturns.js` |
| общие модули | `/var/lib/lunarreturns/tgcloud/lib/*.cjs` |
| база | `/var/lib/lunarreturns/lunarreturns.db` |
| токен | `/etc/lunarreturns/.env` |
| юнит | `/etc/systemd/system/lunarreturns.service` |

Управление дальше: `sudo systemctl restart|stop|disable lunarreturns`.
После обновления ключа — правка `/etc/lunarreturns/.env` и
`sudo systemctl restart lunarreturns`.
После обновления Node или переезда репо — просто повторный запуск
`sudo ~/src/LunarReturns/lunarreturns-install.sh` (пересоберёт юнит).
